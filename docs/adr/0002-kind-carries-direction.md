# 2. 方向由 kind 承载，金额恒为正

- **状态**：已采纳
- **日期**：2026-10-07

## 背景

系统最初只记录**支出**：一个实体、一张表、一个恒为正数的 `amount_cents`。

设计稿（`极简记账`）要求把支出和收入**混排在同一张列表**里，并在头部显示余额。于是必须先回答
一个建模问题：一笔「收入」和一笔「支出」，是同一个实体的两个方向，还是两个不同的东西？

无论选哪种，都要决定**方向存在哪里**。有两条路：

```js
{ amountCents: -3800 }   // 方向 = 金额的符号
{ amountCents: 3800, kind: 'expense' }   // 方向 = 独立的字段
```

符号方案看起来更省事——求和就是 `SUM(amount_cents)`，一个字段搞定。但它有三个代价：

1. **`CHECK (amount_cents > 0)` 必须放宽。** ADR 0001 把这条约束当作「金额是整数分」的第三层
   强制，`docs/verify-rules.md` 剧本 B 实测过：zod 失守时，正是它接住了非法金额。改成有符号金额，
   这条约束就得从 `> 0` 变成 `<> 0`，**整个仓库记录得最完整的硬规则会被悄悄缴械**。
2. **「负的支出」和「正的收入」在数值上无法区分**，退款、冲正这类未来的需求无处安放。
3. **金额的正负号会渗进展示层**，前端每处渲染都要自己判断该不该加 `-`。

这个决定**极难回头**：`kind` 一旦上线，它会同时出现在数据库列、HTTP 契约、前端判别联合和
用户已导出的数据里。反过来，把 `kind` 去掉、改用符号，是一次跨所有层的迁移，而且**迁移前后的
金额语义相同**，没有任何断言能在中途发现迁错了。

## 决定

**一笔交易由「类型 + 金额 + 发生日期 + 分类（仅支出）+ 备注」构成。方向恒由 `kind` 承载，
`amountCents` 恒为正数，任何层都不使用带符号的金额。**

- 实体统一为 **交易 · Transaction**，`kind: 'expense' | 'income'`，取代原先的 `Expense`
- 契约里表达为**判别联合**，而不是「一个大对象 + 可选的 category」：这样
  `transaction.kind === 'expense'` 能在编译期把 `category` 收窄成非空，
  UI 从类型上就不可能给收入渲染分类
- **只有支出有分类**；收入在响应里恒为 `category: null`，在请求里连这个键都不出现
- **余额 = 全部时间的（收入 − 支出）**，与账期无关。它是全系统唯一允许为负的金额字段
- 强制分三层，任何一层单独失守都不会让脏数据落地：

| 层 | 机制 | 位置 |
|---|---|---|
| 文档 | 规则条款 | `CLAUDE.md`、`CONTEXT.md`、`.claude/rules/*.md` |
| 边界 | zod 校验 | `packages/shared/src/schemas.ts` · `TransactionSchema` |
| 存储 | SQL 约束 | `apps/api/src/db/schema.sql` · `CHECK (amount_cents > 0)` 与 `CHECK ((kind = 'expense') = (category IS NOT NULL))` |

## 后果

**收益**

- **ADR 0001 的 `CHECK (amount_cents > 0)` 原封不动地活了下来**，第三层强制没有因为这次扩展而削弱
- 分类枚举从 4 个扩到 8 个**不需要数据迁移**：旧值是新集合的子集
- 一个实体、一张表、一个列表接口，天然满足设计稿的混排；汇总、余额、排序各只写一次
- 「类型与分类必须配对」在文档、zod、SQL 三层都不可表达为错误状态

**代价**

- 收入的报文里带着一个冗余的 `category: null`（请求侧则完全不出现，两侧不对称）
- 判别联合要求调用方先收窄再取值，比单一对象多一步
- 全仓库范围的改名：`Expense` → `Transaction`，连带路由、表名、组件、以及 `CONTEXT.md` 里
  「支出是本系统唯一的领域实体」这句已经不再成立的话
- 已有的数据库文件需要一次真实迁移（`PRAGMA user_version` + `src/db/migrations.ts`），
  因为 `CREATE TABLE IF NOT EXISTS` 改不动既有的表
