# 1. 金额以整数「分」存储

- **状态**：已采纳
- **日期**：2026-10-03

## 背景

记账系统的金额有两种常见建模方式：用浮点数表示「元」（`12.5`），或用整数表示「分」（`1250`）。

浮点数在 IEEE 754 下无法精确表示大多数十进制小数。在 JavaScript 里：

```js
19.99 * 100   // 1998.9999999999998
0.1 + 0.2     // 0.30000000000000004
```

这些误差不会在单笔记录上显现，但会在**累加、比较和分组求和**时累积——而记账系统的核心操作恰恰就是累加和分组求和。

更麻烦的是这个决定**极难回头**：金额会同时存在于数据库、HTTP 响应、前端内存和用户已经导出的数据里。改变单位意味着一次跨越所有层的迁移，而且历史数据可能已经带着无法追溯的舍入误差。

## 决定

**金额在本系统的任何层都以整数「分」表示，字段名一律以 `Cents` 结尾。绝不使用浮点数表示金额。**

- 元 ↔ 分的转换只允许出现在 `packages/shared/src/money.ts` 一处
- 只有展示层才转成元（`formatYuan`）
- 强制分三层，任何一层单独失守都不会让脏数据落地：

| 层 | 机制 | 位置 |
|---|---|---|
| 文档 | 规则条款 | `CLAUDE.md`、`.claude/rules/*.md` |
| 边界 | zod 校验 | `packages/shared/src/schemas.ts` · `CentsSchema` |
| 存储 | SQL 约束 | `apps/api/src/db/schema.sql` · `CHECK (amount_cents > 0)` |

## 后果

**收益**

- 累加与分组求和精确，不存在舍入漂移
- 「这是元还是分」的歧义被字段名的 `Cents` 后缀消除
- 浮点错误在 HTTP 边界上就被拒绝，而不是渗进存储

**代价**

- 每次跨越 UI 边界都要显式转换（`ExpenseForm.vue` 里的 `toCents`），漏转时类型系统不会提醒
- 与使用「元」的外部系统（支付网关、对账文件）对接时，必须在边界处显式换算
- 无法表示小于一分的粒度——本系统不需要，但这条限制是永久性的
